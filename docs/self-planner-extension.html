AL Research Prototype - Devlog 02

Self-Planner Extension

A bounded coding-agent milestone for reducing LLM-teacher dependency through verified procedural memory and domain self-planners.

AL remains a constrained self-learning research prototype. This update extends the original diagnosis-only supervision protocol into a more autonomous Python coding-agent setting.

The goal is not to claim broad coding competence. The goal is to measure whether verified procedures can reduce teacher calls in specific coding task families.

Current framing

From supervised repair to self-planning

The first evidence page measured whether AL could improve under diagnostic supervision, objective verification, and strict teacher limits.

This second milestone asks a narrower follow-up question: can AL reuse verified repair procedures well enough to solve related cold tasks without an LLM teacher?

The answer is currently positive for one bounded real-repo task family: public API and export repair.

What changed

Domain self-planners

AL now includes self-planners for common Python repair classes.

CLI argparse flags
Config, env, and default fallback
SQLite parameterized lookup
Async timeout fallback
API response error shape
Dependency injection formatter
Date and public API export repair

These planners do not replace the verifier. They only produce bounded repair candidates. A task is still verified only by objective checks.

Learning writeback

Procedural memory, not patch memory

Verified episodes now write richer learning records.

This changes memory from “this patch worked once” into “this procedure may apply under these conditions.”

Procedures are only useful if they survive replay or near-transfer checks.

Safety continuity

Same safety protocol

  • Teacher cannot execute tasks.
  • Teacher output is advisory only.
  • Objective verifier is the source of truth.
  • Patches run in branch-copy workspaces.
  • Bad patches do not mutate the main workspace.
  • Verified status cannot come from LLM confidence.
  • Weak or manual-review states are not upgraded into verified.

The LLM is treated as an untrusted teacher or critic, not as a controller.

Review findings

Risks found before final evaluation

  • Crash on unrelated __init__.py files
  • Hardcoded items in dependency-injection planner
  • Patching the wrong first function
  • Overly destructive SQLite rewrite
  • Hardcoded args.message in CLI planner

These were fixed before the final hard batch.

This is part of the safety signal: planner errors were treated as failure modes, not hidden.

The main evaluation used a real Click repository copy.

AL completed 20/20 bounded cold tasks without calling the LLM teacher.

The evaluated task family involved real files in the Click repository, especially public API/export boundaries and related modules.

This is not evidence of broad autonomous coding competence. It is evidence that verified self-planners can replace teacher calls in a bounded real-repo repair family.

Harness correction

An early run exposed a benchmark setup issue: pytest imported the installed click package instead of the repository copy.

The harness was corrected by clearing sys.modules['click*'] before test execution.

Another false failure came from an assertion that did not match real Click behavior for click.core.batch. The contract was corrected and the evaluation was repeated.

These corrections are part of the reported evidence because benchmark validity is part of the protocol.

Main text

Toward bounded self-planning

This milestone extends AL from diagnosis-only supervised repair toward bounded self-planning.

The previous baseline showed that AL could act first, receive diagnosis-only teacher feedback after failure, verify objectively, and promote procedures only after replay or near-transfer.

This update shows that, after adding domain self-planners and richer procedural memory, AL can solve one real-repo task family without LLM teacher calls.

The strongest current signal is not general coding ability. The signal is teacher-dependency reduction under objective verification.

What this shows

Narrow but important result

This milestone supports the following claim:

For bounded Python repair families, verified procedures can reduce LLM-teacher dependency while preserving objective verification and false-success controls.

The result is especially relevant to agentic oversight because the LLM is not trusted as the source of truth.

AL controls scope, patching, verification, memory promotion, and final status.

What this does not show

Current boundaries

  • Codex-level coding ability
  • Large architectural refactor reliability
  • General repo understanding across arbitrary projects
  • Strong performance without tests
  • Universal tool execution
  • Broad multi-language capability

The current result is strongest for public API/export repair and related bounded Python tasks.

Limitations

Current boundaries of this milestone

  • The Click batch focused on one task family.
  • The task family is real-repo, but still bounded.
  • Large refactors remain unproven.
  • Work without tests still falls back to weak or manual-review states.
  • Tool execution is not yet fully unified inside the supervisor loop.
  • Memory needs more verified episodes across more domains.
